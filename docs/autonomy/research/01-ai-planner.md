# 01 — The robot's "brain": planner, VLM and VLA architectures for a Unitree G1 EDU

Research date: 2026-11-02. Scope: high-level autonomy for a G1 EDU (29 DoF, 2x BrainCo hands, D435i, Mid-360, Orin NX 16 GB on JetPack 5) that today runs an off-board LLM calling ~28 fixed skills.

Every claim has a link. Where sources disagree or I could only find secondary coverage, it says so. "Verified" means I read the primary page (vendor docs, repo README, official blog) during this research.

---

## TL;DR

1. **Keep the design rule, but make the loop closed.** "The LLM issues skills and is never in the motor loop" is how every working 2026 humanoid stack is built: Figure Helix (S2 at 7-9 Hz over S1 at 200 Hz), Gemini Robotics-ER 2 (an orchestrator that calls VLAs and navigation as _tools_), Stanford HomeBody on a G1 (a frontier VLM calling Navigate/Pick/Place/Open-drawer skills). What's missing from the current stack is **perception-grounded verification and replanning**: look, act, check, retry.
2. **The biggest quick win is grounding, not a VLA.** Give the planner a `look()` tool and a pointing VLM (Gemini Robotics-ER 2 returns `[y,x]` points normalized to 0-1000). Deproject the point with D435i depth and transform it into the FAST-LIO map frame. That turns "the glass on the table" into coordinates for Nav2 and arm IK. This is the HomeBody recipe, running on a G1.
3. **VLAs come second, as extra skills.** Train a small set of dexterous tasks on G1 teleop data: pi0.5 through openpi/LeRobot (LeRobot documents pi05 on the G1), or GR00T N1.7 (NVIDIA ships a G1 deployment path in Isaac ROS). Run them **off-board on an RTX 4090/5090-class GPU**, not on the JetPack 5 Orin NX. Wrap each one as a skill with a timeout and a success check.
4. **Safety stays outside the AI.** Put a deterministic governor between every AI output and the robot. It enforces velocity and workspace limits, slows or stops for nearby people using LiDAR, keeps a heartbeat/deadman, and leaves the hardware e-stop and the Unitree damping mode untouched. Google itself says its on-device VLA "does not include built-in semantic safety features" and recommends trusted low-level controllers.

**Recent G1-specific evidence that this layer works:**

- _Hierarchical Vision-Language Planning for Multi-Step Humanoid Manipulation_ runs a low-frequency VLM planner that sequences imitation-learned skills from a structured skill library, plus a higher-frequency VLM execution monitor. It was validated on a 29-DoF G1 ([arXiv 2506.22827](https://arxiv.org/html/2506.22827v1), per its abstract/search snippet).
- **HomeBody** (Stanford TML, Sept 2026) puts a frontier VLM (the page calls it "GPT Astra") over composable skills on a G1: Navigate, Pick, Place, Open drawer, Pick from drawer. It has **no learned VLA**, persistent spatial memory, and bounded local retries. Failed skills "return the reason to the VLM, which can replan." Perception and skills run on an RTX 4090 laptop and the VLM runs remotely. The page lists its own limitations: pauses between skills while the model reasons, finger servos overheating, and some grasps needing retries ([project page](https://tml.stanford.edu/homebody/), code linked at github.com/Stanford-TML/homebody). **This is the closest published match to what this team should build.**
- **KINO** (arXiv 2609.18869, Sept 2026): a VLM picks keyframes from a predefined library, and a whole-body policy on a real G1 tracks them for pickup and transport ([arXiv HTML](https://arxiv.org/html/2609.18869v1); I only read the search abstract).

**Tooling note:** Open ROS-over-MCP bridges exist (robotmcp/ros-mcp-server; it uses rosbridge and exposes topics, services and actions to MCP clients such as Claude) ([listing](https://mcp.directory/servers/ros-mcp-server), [docs index](https://docsearch.algolia.com/mcp/docs/repo/robotmcp/ros-mcp-server)). Don't expose raw `/cmd_vel` through them. Keep exposing _skills_, which you already do.

## 2. VLMs for embodied reasoning and spatial grounding

### Gemini Robotics-ER 2 (Google DeepMind) — current, public API

- **Released July 30, 2026** as a public preview in the Gemini API and AI Studio, with a private preview on Gemini Enterprise Agent Platform ([Google blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/), [Gemini API changelog](https://ai.google.dev/gemini-api/docs/changelog)). The Google Cloud model page gives Oct 27, 2026 as its date, which is probably the Cloud listing date ([Cloud page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/robotics-er-2)).
- **Model IDs:** `gemini-robotics-er-2-preview` (built on Gemini 3.5 Flash; supports code execution and batch) and `gemini-robotics-er-2-streaming-preview` (Live API, low-latency bidirectional streaming, function calling, no code execution). **ER 1.6 (`gemini-robotics-er-1.6-preview`) was deprecated Aug 31, 2026** ([docs](https://aistudio.google.com/docs/robotics-overview), [model page](https://ai.google.dev/gemini-api/docs/models/gemini-robotics-er-2-preview)).
- **Capabilities:** pointing, video tracking, bounding boxes, trajectories, success detection, task-progress classification and moment finding (video), instrument reading, function calling to orchestrate "VLA models or navigation APIs as tools," and multi-robot coordination. Inputs are text, image, video and **audio**. Input limit is 131k tokens, output 65k ([docs](https://aistudio.google.com/docs/robotics-overview), [blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)).
- **Point format:** a JSON list of `{"point": [y, x], "label": ...}`, normalized 0-1000 ([docs](https://aistudio.google.com/docs/robotics-overview)).
- **Latency:** `thinking_level` trades latency for quality, and Google recommends `medium`. The blog says sub-second latency matters and that the streaming endpoint avoids "stop-and-think" pauses, but it **gives no absolute latency numbers** ([docs](https://aistudio.google.com/docs/robotics-overview), [blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)).
- **Safety:** Google reports better results than ER 1.6 on "Safety Instruction Following" and "Human Proximity," and a demo halts a humanoid when a person comes near. It also says the developer is responsible for safety, and the docs carry a privacy notice about recording people ([blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/), [docs](https://aistudio.google.com/docs/robotics-overview)).
- **Demos:** Spot, Apptronik Apollo 2, Franka. No Unitree robots are shown ([blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)).
- Some secondary sites claim "Gemini Robotics 2" (a VLA) and "On-Device 2" launched alongside ER 2 ([eesel.ai](https://www.eesel.ai/blog/gemini-robotics-2), [beehiiv](https://roo.beehiiv.com/p/gemini-robotics-er-2-explained)). **I could not confirm this on Google's own page. Treat it as unverified.**

### GPT / Claude vision as the planner

- Frontier general models work fine as the System 2 planner. HomeBody runs on a remote frontier model ([HomeBody](https://tml.stanford.edu/homebody/)). Anthropic's Project Fetch shows Claude helping build and run a Unitree Go2 fetch behavior. Anthropic's own phase-two page says the models "still struggled" with the precise physical part ([phase 1](https://www.anthropic.com/research/project-fetch-robot-dog), [phase 2](https://www.anthropic.com/news/project-fetch-phase-two)).
- **Practical split:** let the general LLM (campus gateway or Claude) do dialogue, task decomposition and tool calls. Delegate **pixel-precise** grounding (points, boxes, success checks) to a spatially trained model: ER 2, Molmo, or RoboPoint. General chat models are less reliable at precise pointing than models trained for it, and ER 2's benchmarks are positioned exactly on that gap ([blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)).

### Open spatial-reasoning / pointing models (self-hostable)

- **Molmo** (Ai2, 2024) is an open VLM trained with 2D pointing data ([arXiv 2409.17146](https://arxiv.org/abs/2409.17146)). **MolmoAct 2** (May 5, 2026) is an open robot model built on **Molmo 2-ER** (embodied reasoning). Ai2 reports 450 ms per action call for the base model and 1,300 ms with adaptive depth reasoning, plus a 720 h bimanual dataset ([Ai2 blog](https://allenai.org/blog/molmoact2), [SiliconANGLE](https://siliconangle.com/2026/05/05/ai2-releases-molmoact-2-enhancing-robot-intelligence-real-world/)). Molmo 2-ER is a candidate for an **on-prem pointing model** if cloud is unavailable.
- **RoboPoint** predicts affordance points from language, e.g. "free space left of the mug" ([arXiv 2406.10721](https://arxiv.org/abs/2406.10721)). **SpatialVLM** covers metric spatial VQA, e.g. "how far is X from Y" ([arXiv 2401.12168](https://arxiv.org/abs/2401.12168)).
- **NVIDIA Cosmos-Reason2** (2B/8B, Qwen3-VL based, released Dec 19, 2025) is an open reasoning VLM with robot chain-of-thought prompt templates. It needs ≥24 GB of GPU memory for 2B and ≥32 GB for 8B. Official validation covers only Hopper/Blackwell, and Jetson Thor support is "coming soon" for vLLM ([repo index](https://docsearch.algolia.com/mcp/docs/repo/nvidia-cosmos/cosmos-reason2)). It is an off-board fallback planner/verifier, **not something for the Orin NX**.

### Zero-shot manipulation via VLM + constraints (no robot training data)

- **VoxPoser** composes LLM-written code with a VLM into 3D value maps that a motion planner follows ([arXiv 2307.05973](https://arxiv.org/abs/2307.05973)).
- **ReKep** has a VLM write keypoint-relation constraints (Python cost functions) that an optimizer solves at high rate ([arXiv 2409.01652](https://arxiv.org/abs/2409.01652)).
- **MOKA** has a VLM mark keypoints and waypoints on the image, which are converted into motions ([arXiv 2403.03174](https://arxiv.org/abs/2403.03174)).
- **Assessment:** these are conceptually elegant and need no demos. They are good for **simple, rigid, tabletop** actions (push, place, open) when combined with the BrainCo grasp presets. They are brittle for dexterous in-hand work, and none of them was shown on a G1. The MOKA-style "point → keypoint → IK" pattern is the pragmatic version, and HomeBody's Pick skill is exactly that: VLM point → SAM mask → stereo depth → analytic grasp ([HomeBody](https://tml.stanford.edu/homebody/)).

Every open VLA still needs **robot-specific demos for each task family** before it is reliable on a new embodiment, and none of the open ones has been shown doing general household work on a G1 with BrainCo hands. Expect a handful of trained skills, not open-ended dexterity.

## 4. Hierarchical System 2 / System 1 (/ System 0) design

**How production systems hand off:**

- **Latent handoff** (Figure Helix): S2 outputs a continuous latent vector at 7-9 Hz that conditions S1 at 200 Hz. This needs joint training, so it's out of reach for a student team ([Figure](https://www.figure.ai/news/helix)).
- **Language/tool handoff** (Gemini Robotics-ER 2 → VLA, HomeBody, Hi Robot [arXiv 2502.19417](https://arxiv.org/abs/2502.19417)): S2 emits a short instruction or a typed skill call ("pick(cup, point=[412,530], hand=right)"). S1 runs until it finishes or times out, then reports success or failure. **This is the right handoff for this team.** It is debuggable, each layer can be swapped independently, and it is compatible with MCP / OpenAI tool calling.
- **Three tiers** (Helix 02, GR00T + SONIC, LeRobot + Holosoma):
  - S2: planner, ~0.1-1 Hz.
  - S1: VLA or skills, 10-50 Hz action chunks.
  - S0: whole-body balance/locomotion RL policy at 50-500 Hz on the robot.

**Recommended layering for this robot:**

```
[Voice: Vosk/faster-whisper/Piper — local]          [Operator UI / VR]
              |                                            |
     S2  Planner agent (cloud LLM: campus GPT / Claude)  ← world-state + memory tools
              |  typed tool calls only (skill, args, timeout)
     Grounding tools: look(), point(query) → Gemini Robotics-ER 2 (cloud) or Molmo 2-ER (off-board GPU)
              |  verify(skill) → ER 2 success detection / progress
     S1  Skill executor (ROS 2): walk_to, turn, gestures, pick/place (point→grasp), vla_task(name, instr)
              |      ↳ VLA server on off-board GPU (pi0.5 / GR00T N1.7), action chunks @ 30-50 Hz
     ===== SAFETY GOVERNOR (deterministic, on Orin NX, no ML in the decision path except person detection) =====
              |  clamps, geofence, human-proximity slow/stop, heartbeat, skill/arg whitelist
     S0  Unitree loco controller / GR00T-WBC / SONIC / Holosoma  →  joints
     Hardware e-stop + Unitree remote damping (untouched by software)
```

**Keeping safety outside the AI** (deterministic and testable; every AI-generated action passes through it):

- **Hardware layer:** physical e-stop and the Unitree remote's damping/stop, which never depend on any software path you write.
- **Governor node** on the Orin NX (ROS 2):
  1. **Whitelist:** only catalogued skills, with typed and bounded arguments, e.g. `walk_to` only inside a Nav2 keepout-filtered map, arm targets only inside a reachable workspace box.
  2. **Velocity and acceleration caps** on base twist and arm joint velocity. VLA chunks get clipped or rejected before they reach the controller.
  3. **Human proximity:** use Mid-360 points plus the YOLO `person` class to scale speed down near people and stop inside a radius. ER 2 shows the same behavior ("halts a humanoid when a person is nearby"), but **don't depend on the cloud for it** ([blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)).
  4. **Heartbeat/deadman:** if the planner, VLA server or network is silent for more than N ms during a motion skill, go to a safe stop (stand still, hands open-and-hold). This matters because S1 runs off-board over Wi-Fi.
  5. **Timeouts and bounded retries** per skill, the same as HomeBody's "bounded local retries" ([HomeBody](https://tml.stanford.edu/homebody/)).
  6. **Confirmation gates** for risky intents (handing objects to people, carrying liquids, anything near stairs). This is KnowNo's "ask for help when uncertain" ([arXiv 2307.01928](https://arxiv.org/abs/2307.01928)).
- **Context:** Google notes Gemini Robotics On-Device "does not include built-in semantic safety features" and recommends trusted low-level controllers ([DeepMind](https://deepmind.google/discover/blog/gemini-robotics-on-device-brings-ai-to-local-robotic-devices/)). The dedicated humanoid standard **ISO 25785-1** (dynamically stable mobile robots, fall risk) was still a **working draft in early 2026**; ISO 10218:2025 still applies ([i-scoop](https://www.i-scoop.eu/iso-25785-1-explained-and-what-it-means-for-humanoid-robot-safety/), [robottoday](https://robottoday.com/article/humanoid-robotics-standards-heis-2026-vs-the-international-landscape)).

## 5. Memory, world state and grounding "the glass on the table"

**The grounding chain (works with today's hardware):**

1. The planner calls `point("the glass on the table")` with the current D435i RGB frame.
2. ER 2 returns `[y, x]` in 0-1000 ([docs](https://aistudio.google.com/docs/robotics-overview)). Convert it to pixels and read the aligned depth there (median over a small patch, or a SAM mask). Deproject with the D435i intrinsics to get a camera-frame XYZ.
3. Transform with TF (camera → torso → FAST-LIO `map`). You now have a map-frame point. Nav2 gets a standoff pose facing it, and arm IK gets the torso-frame target (LeRobot's G1 integration uses pinocchio/CasADi for arm IK ([LeRobot G1](https://huggingface.co/docs/lerobot/unitree_g1))).
4. During approach, **track** the target instead of asking the VLM again. HomeBody uses SAM 2.1 + SAMURAI tracking and visual servoing so the robot doesn't wait on a VLM call each step ([HomeBody](https://tml.stanford.edu/homebody/)).
5. Call `verify()` after the skill.

**Why YOLO11n-COCO is not enough on its own:** it only knows 80 COCO classes and can't resolve referring expressions ("the _red_ glass _on the left_"). Keep it for fast person and common-object detection feeding the governor and memory. Use the VLM for open-vocabulary grounding.

**World-state memory (pick the lightest that works):**

- **Object memory table (start here):** `{id, label, caption, map_xyz, last_seen, image_crop, confidence}`. Fill it from YOLO detections and VLM `describe()` calls, and expose it as planner tools: `find_object(query)` and `where_was(query)`. This is HomeBody's idea of storing ego observations with descriptions in a shared frame so it can recall objects that are out of view ([HomeBody](https://tml.stanford.edu/homebody/)).
- **Open-vocabulary 3D scene graphs (later):**
  - **ConceptGraphs**: objects as nodes with captions, relations from an LLM ([arXiv 2309.16650](https://arxiv.org/abs/2309.16650)).
  - **HOV-SG**: floor → room → object hierarchy ([arXiv 2403.17846](https://arxiv.org/abs/2403.17846)).
  - **DovSG**: dynamic updates as the robot changes the scene, with GPT-4 decomposing tasks over the graph ([arXiv 2410.11989](https://arxiv.org/html/2410.11989v3)).
  - 2026 relation-aware 3DSG work for LLM command grounding ([arXiv 2602.02456](https://arxiv.org/abs/2602.02456v1), [arXiv 2602.04635](https://arxiv.org/abs/2602.04635v1)).
  - These are research-grade and GPU-heavy. They're worth it only once multi-room tasks matter.
- **Episodic memory:** an append-only log of `(time, utterance, plan, skill calls, results, keyframes)` that the planner can search ("what did you do with my keys?"). PI's 2026 work on VLAs with long and short-term memory points the same way for S1 ([PI](https://www.pi.website/research/memory)).
- **Landmarks you already have** (named poses) become graph nodes: rooms and places that objects belong to.

## 7. Recommendation: a staged plan for a student team (6-12 months)

### Stage A (weeks 0-6): closed-loop agent over the existing skills. Highest value, lowest risk.

- Keep the ~28 skills and the "LLM issues skills only" rule.
- Add these tools:
  - `look()`: returns the current RGB frame or a caption.
  - `point(query)`: ER 2 point → depth → map XYZ.
  - `verify(skill_id)`: ER 2 success detection on before/after frames.
  - `find_object(query)` / `remember(...)`: object memory table.
  - `ask_user(question)`: KnowNo-style clarification.
- Make the planner loop ReAct + Inner Monologue: plan → act → verify → replan, with bounded retries.
- Model choice:
  - **Planner:** whatever is strongest on the campus gateway, or Claude via MCP (already working).
  - **Grounding/verification:** `gemini-robotics-er-2-preview` at `thinking_level=medium`. Try `-streaming-preview` later for live "watch and react."
- Build the **safety governor** now, before any new motion capability.
- Exit test: "go to the kitchen, find a cup, and tell me what's in it" works in many phrasings, and the robot recovers from at least one injected failure.

### Stage B (months 2-5): open-vocabulary manipulation without learning

- `pick(point, hand)` / `place(point)` / `point_at(query)` / `give_to_person()`: VLM point → SAM mask → D435i depth → analytic grasp → IK, with BrainCo grasp presets (power/pinch). This is the HomeBody/MOKA pattern ([HomeBody](https://tml.stanford.edu/homebody/), [MOKA](https://arxiv.org/abs/2403.03174)).
- Optional: let the planner emit **behavior trees** for repeated missions, validated against the skill schema.
- Upgrade memory to a lightweight scene graph (rooms from landmarks, objects with relations) only if tasks need it.

### Stage C (months 4-10): learned System 1 for a few dexterous tasks

- **Prerequisite:** an off-board RTX 4090/5090 server, and either a JetPack 6 path or accepting that the VLA runs off-board.
- Collect **50-200 teleop demos per task** with `xr_teleoperate` + BrainCo → LeRobot format ([xr_teleoperate](https://www.sourcepulse.org/projects/1381678)).
- **Option 1 (recommended first): π0.5 via LeRobot/openpi.** It's open, LoRA fits a 4090, LeRobot documents pi05 training and RTC rollout on the G1 ([LeRobot G1](https://huggingface.co/docs/lerobot/unitree_g1), [openpi](https://github.com/Physical-Intelligence/openpi)).
- **Option 2: GR00T N1.7** with the `UNITREE_G1` embodiment tag and the Isaac ROS G1 deploy package. It is NVIDIA's own G1 path and fine-tunes on a rented ≥40 GB GPU ([repo](https://github.com/NVIDIA/Isaac-GR00T)). Note that the Isaac ROS package is **ROS 2 Jazzy**, so check that against your ROS distro.
- Optional (Unitree-native): **UnifoLM-VLA-0**, which is pre-trained on G1 data ([project](https://unigen-x.github.io/unifolm-vla.github.io)).
- Expose each trained policy as `vla_task("wipe_table")` with a timeout, governor clipping and `verify()`.
- Lower body: start with arms-only VLA while standing on the stock controller. Try GEAR-SONIC/Holosoma for loco-manipulation only if a task truly needs it.

### Stage D (stretch, 9-12+ months)

- GR00T N2 if it ships ([THG](https://thehumanoidgroup.com/news/article/nvidia-gr00t-n2-preview-gtc-2026)).
- Pi API beta (waitlist) ([PI](https://www.pi.website/blog/api-beta)).
- Gemini Robotics VLA / On-Device trusted-tester access ([DeepMind](https://deepmind.google/discover/blog/gemini-robotics-on-device-brings-ai-to-local-robotic-devices/)).
- Thor dock to move S1 onboard.

### What "do anything" realistically means at month 12

- **Achievable:** open-ended _conversation and reasoning_; finding, navigating to, pointing at, describing and remembering arbitrary objects; simple pick/place of rigid objects; 3-6 trained dexterous tasks; graceful refusal or asking for clarification for everything else.
- **Not achievable at month 12 with open models on this hardware:** robust dexterous manipulation of arbitrary objects, arbitrary whole-body tasks, multi-minute unsupervised household chores. Figure needed ~500 h of teleop for Helix ([Figure](https://www.figure.ai/news/helix)), and Unitree used ~340 h of G1 data for UnifoLM-VLA-0 ([project](https://unigen-x.github.io/unifolm-vla.github.io)).
