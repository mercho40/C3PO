# 03 — Mapping, semantic memory and autonomous navigation for the C3PO G1

Research date: 2026-11-02. Scope: Unitree G1 + Livox Mid-360 + RealSense D435i + Jetson Orin NX 16 GB (JetPack 5, 6 allowed), FAST-LIO2 → pointcloud_to_laserscan → Nav2 (DWB) in a ROS 2 Humble container, cmd_vel → Python bridge → G1 high-level velocity API, LLM agent fed a JSON world summary + YOLO11n detections, named landmarks in a DB.

Goal behaviours: "go find the glass", "go to the kitchen", "explore the room", "follow me".

> **Method note.** Claims are cited per line. Direct arXiv full-text fetches timed out from this sandbox, so several 2026 paper details (success rates, hardware splits) come from search-indexed abstracts, project pages or secondary summaries. Those are marked _(secondary)_. Check the paper tables before quoting numbers in the thesis.

---

## TL;DR: top recommendation

1. **Fix the map frame first.** FAST-LIO2 is odometry only, so the landmarks in the DB drift between sessions. Build one map, then **localize against it on every boot**. The cheapest path reuses the `/scan` the stack already produces: **slam_toolbox mapping → serialized pose graph + `.pgm` → slam_toolbox localization mode**, with FAST-LIO2 as `odom`. If 2D relocalization proves flaky on the swaying humanoid, upgrade to the G1-specific **deepglint FAST_LIO_LOCALIZATION_HUMANOID** (Humble branch, handles the G1's upside-down Mid-360) or **lidar_localization_ros2** (NDT/GICP, Nav2 launch files).
2. **Persistent semantic memory: a lightweight object DB, not a research scene graph.** YOLO detection + D435i depth → 3D point → TF to `map` → upsert by (class, distance < ~0.5 m) with `seen_count`, `last_seen`, `confidence`. COCO already has `cup` and `wine glass`. Add **YOLOE** (open-vocabulary, Ultralytics) only when you need classes outside COCO. Rooms ("kitchen") are polygons/landmarks in the existing DB.
3. **Give the LLM a few long-running tools, with progress and cancel**: `navigate_to(object_id | landmark | pose)`, `find(query)`, `explore(region?)`, `look_around()`, `follow_person(track_id?)`, `stop()`, `get_task(task_id)`. Each wraps a Nav2 action (NavigateToPose feedback already carries distance/time remaining and recovery count).
4. **"Find X" = memory first → else frontier exploration with an LLM/VLM choosing the frontier (VLFM / SG-Nav / OpenFrontier style) → verify with the detector → stop within 1 m.** Use m-explore-ros2 for plain "explore the room".
5. **"Follow me" = BoT-SORT person track + depth → PoseStamped in `map` → Nav2 FollowPoint BT (Humble) / Following Server (Jazzy+).**
6. **Controller: replace DWB with MPPI (Omni model; the G1 can strafe) or RPP + RotationShim.** Keep speed ≤ 0.5 m/s, filter the robot's own body out of the scan, add the Collision Monitor, and mark stairs as keep-out zones.
7. **Compute:** everything geometric plus YOLO/tracking runs on the Orin NX. The LLM and any VLM run off-board, as every 2026 G1 object-nav paper found does. JetPack 6 is needed only for Isaac ROS 3.x nvblox or GLIM, so it is not on the critical path.
8. **Evaluate:** ≥ 20 trials per task type, split "object already in memory" vs "requires exploration". Success = stopped within 1 m with the object visible (Habitat ObjectNav). Also report SPL, time, and human interventions.

### 1.3 Recommended: a lightweight object database

Nothing above runs comfortably on an Orin NX next to FAST-LIO + Nav2 + YOLO. What C3PO needs is "where did I last see a glass?", so a small table is the right size:

```
objects(id, class, label, x, y, z  -- in map frame
        conf_max, seen_count, first_seen, last_seen, room_id, thumbnail_ref)
```

- **Insert/upsert:** for each detection, take the median D435i depth in the box (or its mask), deproject with the camera intrinsics, transform `camera → map` with TF at the image timestamp. Match an existing row if `class` matches and the distance is < 0.5 m (larger for furniture). Otherwise insert a new row. Update the position with a running mean and bump `seen_count`/`last_seen`.
- **Forgetting:** when the robot is within view range of a row's position, the region is in the camera frustum, and nothing is detected for N frames, decrement confidence. This is the "map update" behaviour ConceptGraphs advertises ([project](https://concept-graphs.github.io)) at a fraction of the cost.
- **Vocabulary:** YOLO11n (COCO) already covers `cup`, `wine glass`, `bottle`, `chair`, `couch`, `refrigerator`, `person`… For open vocabulary use **YOLOE**: text/visual/prompt-free modes, zero overhead when used closed-set, in Ultralytics ([docs](https://docs.ultralytics.com/models/yoloe), [arXiv 2503.07465](https://arxiv.org/html/2503.07465v2)); YOLOE-26 is NMS-free ([arXiv 2602.00168](https://arxiv.org/pdf/2602.00168)). **NanoOWL** (OWL-ViT on TensorRT) officially supports Orin NX 16 GB ([Jetson AI Lab](https://www.jetson-ai-lab.com/tutorials/nanoowl), [GitHub](https://github.com/NVIDIA-AI-IOT/nanoowl)). Grounding DINO 1.6 Edge ~14–15 FPS on Orin NX _(secondary, [Fora Soft](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/open-vocabulary-detection-grounding-dino-florence-2-rtdetr-rfdetr))_. For the accuracy/latency trade-off on Orin, see [Frontiers 2025](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2025.1693988/full).
- **LLM view:** serialize the table into the existing JSON world summary as `{id, class, room, distance_m, last_seen_s_ago, confidence}`. ConceptGraphs' key insight is that an object graph turns cheaply into text for LLM planning ([arXiv 2309.16650](https://arxiv.org/pdf/2309.16650)).
- **Rooms:** "kitchen" = a landmark pose + optional polygon in the existing DB, i.e. the room layer of HOV-SG/Hydra done by hand. Later the LLM can infer room labels from co-occurring objects (fridge + sink → kitchen), as SG-Nav and UniGoal do with their graphs.

**Recommended path:**

1. **Now:** `slam_toolbox` in mapping mode on the existing `/scan`, with FAST-LIO2 as `odom`. Drive the space once. Save the serialized pose graph + `.pgm`. Every boot: slam_toolbox **localization mode** (or AMCL + `map_server`) → `map→odom`. No new dependencies, and it is the Nav2-native path.
2. **If 2D relocalization is unreliable** (humanoid sway tilts the scan plane; glass and clutter): save FAST-LIO2's PCD (the `/map_save` service in common ROS 2 forks, [zenn write-up](https://zenn.dev/nutechr/articles/e80f708a1c7506)), clean it in CloudCompare, and run **deepglint's Humble branch** or **lidar_localization_ros2** for 3D `map→odom`. Keep slam_toolbox's `.pgm` (or project the PCD) as the Nav2 static layer.
3. **Do not** chase lifelong mapping; it is experimental. Re-map when furniture moves a lot; the object DB handles small changes.

## 3. Object-goal navigation and exploration

### 3.1 Classical frontier exploration

- **m-explore-ros2 / explore_lite:** Humble port. Consumes a costmap and sends Nav2 goals. `explore/resume` pauses/resumes, `return_to_init`, `min_frontier_size` ([GitHub mirror](https://github.imc.re/robo-friends/m-explore-ros2), [Husarion tutorial](https://husarion.com/tutorials/ros2-tutorials/10-exploration/)). It needs a growing occupancy grid, which slam_toolbox in mapping mode provides.
- **frontier_exploration_ros2** (Humble/Jazzy): self-reported 22% shorter distance than m-explore ([Discourse](https://discourse.openrobotics.org/t/frontier-exploration-ros2-modern-autonomous-exploration-system-for-ros-2/57222)). **Roadmap Explorer** also lists Humble ([index](https://index.ros.org/r/roadmap_explorer/)).

### 3.2 VLM/LLM-guided object search (zero-shot, modular)

| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **VLFM** (ICRA 2024)                        | Frontiers from depth occupancy + VLM image-text similarity → "value map" → go to the best frontier                     | **Spot** in an office, no prior map; code [bdaiinstitute/vlfm](https://www.github.com/bdaiinstitute/vlfm) ([arXiv 2312.03275](https://arxiv.org/abs/2312.03275))                                                 |

**Takeaway for C3PO:** OpenFrontier's and VLFM's structure maps directly onto what C3PO already has. Nav2 executes. Frontiers come from the occupancy grid. The **off-board LLM/VLM only chooses which frontier or room to try next**, given the world summary plus a camera frame per candidate direction. The detector plus a verification step (DRIVE-Nav / SG-Nav re-perception) decides success.

**Verdict:** impressive, and NaVILA did run on a G1, but these models need a 7B-class GPU off-board. They emit low-level motion that bypasses Nav2's costmaps and Collision Monitor, and they do not use your map, DB or landmarks. Keep them as a stretch experiment ("NaVILA-mode" vs "Nav2-mode" makes a good thesis comparison), not the backbone.

## 4. Person following and human-aware navigation

- **Tracking:** Ultralytics `model.track()` supports **BoT-SORT (default) and ByteTrack**. BoT-SORT has optional ReID (`with_reid`), which matters for re-acquiring "the person who said follow me" after occlusion ([Ultralytics track docs](https://docs.ultralytics.com/modes/track?h=track)). C++ BoT-SORT runs real-time on Jetson NX ([BoTSORT-cpp](https://github.com/viplix3/BoTSORT-cpp)).
- **Target pose:** box → D435i depth → `map`-frame PoseStamped, low-pass filtered. Use the Mid-360 points inside the person's bearing as a fallback beyond the D435i's useful depth range.
- **Nav2 following:**
  - **Humble:** the **FollowPoint** behaviour tree replans at 1 Hz toward a pose on `goal_update`, and `TruncatePath` stops ~1 m short so the robot does not drive into the person ([FollowPoint BT](https://docs.nav2.org/behavior_trees/trees/follow_point.html), [tutorial](https://navigation.ros.org/tutorials/docs/navigation2_dynamic_point_following.html)).
  - **Jazzy+:** a dedicated **Following Server** (`opennav_following`, action `follow_object`, `desired_distance` 1.0 m, `detection_timeout` 2 s, `pose_topic`, optional `search_by_rotating`) ([config](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/others/configuring_following_server/), [FollowObject BT node](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/core_servers/bt_plugins/actions/FollowObject/), [API](https://api.nav2.org/nav2-jazzy/html/following__server_8hpp_source.html)).
- **Social layers:** `nav2_social_costmap_plugin` (proxemics + passing in one layer, tested on Humble, consumes `/people`) ([GitHub](https://github.yxlr123.workers.dev/robotics-upo/nav2_social_costmap_plugin)). Benchmarked in HuNavSim, where it keeps more distance and yields more ([arXiv 2305.01303](https://arxiv.org/pdf/2305.01303)). Nav2CAN adds group (F-formation) awareness ([AAU paper](https://vbn.aau.dk/ws/files/561057816/Nav2CAN_conference_paper.pdf)). nvblox's people layer is the GPU alternative (§1.1).
- **Uni-NaVid** does human following end to end ([arXiv 2412.06224](https://arxiv.org/pdf/2412.06224)), a research alternative only.

## 5. Humanoid-specific navigation issues

- **Velocity API:** G1 `LocoClient.SetVelocity(vx, vy, omega, duration=1.0)` in m/s and rad/s. `Move(..., continous_move=True)` sets an effectively infinite duration ([DeepWiki unitree_sdk2](https://deepwiki.com/unitreerobotics/unitree_sdk2/8-high-level-control-apis), [unitree_ros2 LocoClient](<https://deepwiki.com/unitreerobotics/unitree_ros2/5.5-lococlient-(g1)>)). **Prefer short durations (≈ 2–3× the cmd_vel period) so a dead bridge stops the robot.** `SetSpeedMode` 0–3 caps max running speed; the service is named `sport` from ai_sport 8.2.0.0, `loco` before ([doc mirror](https://unidocs.2vzdtw8.duckdns.org/doc/home_en_G1_developer_rpc_routine.md)). Top speed is ~2 m/s _(secondary)_, with ~1.5 m/s comfortable on flat floors ([review](https://roboticscenter.ai/en/blog/unitree-g1-review)). **Arm control at full weight makes the G1 ignore velocity commands** ([knowledge base](https://vat.pages.dev/RoboticsKnowledgebase/roboticsknowledgebase.github.io/blob/e25f04f00ad0e76d908d3c07dc21e95907be312e/wiki/common-platforms/unitree-g1.md)), which matters if the agent gestures while walking.
- **RL policies vs the built-in controller:** NaVILA uses its own RL locomotion ([legged-loco](https://github.com/yang-zj1026/legged-loco)). SysNav drives the G1 over the standard interface (WebRTC) ([gitee](https://gitee.com/EricGao2020/SysNav)). For a thesis project the built-in controller plus Nav2 is the sane choice. Custom low-level policies mean leaving the sport/loco service and taking on fall risk.
- **Controller choice:**
  - **DWB** is fast but hugs obstacles; comparison tables list legged support as absent.
  - **MPPI** lists legged/non-circular support (Macenski, [ROSCon 2023](https://roscon.ros.org/2023/talks/On_Use_of_Nav2_MPPI_Controller.pdf)). It has an **Omni** motion model with `vy_max`/`ay_*` for lateral motion ([config](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/controller_plugins/mppi_controller/configuring_mppic/)), and the G1 accepts `vy`.
  - **RPP** now supports legged robots and is smooth and cheap, but weak in dynamic scenes ([Discourse](https://discourse.openrobotics.org/t/nav2-new-controller-plugin-regulated-pure-pursuit/18928)). Pair it with the **RotationShimController** to turn in place before tracking ([tutorial](https://docs.nav2.org/tutorials/docs/using_shim_controller.html)).
  - **Recommendation:** MPPI (Omni) first. Fall back to RPP + RotationShim if Orin CPU load becomes a problem. No humanoid-specific benchmark exists, so tune on the robot.
- **Speed and acceleration:** start with `vx ≤ 0.5`, `vy ≤ 0.2`, `ωz ≤ 0.6`, gentle accelerations. Gait response lags far more than a wheeled base, so use the Nav2 velocity smoother and the Collision Monitor (stop/slow polygons) in front of the bridge.
- **Footprint and scan:** a circular footprint radius ≈ half the shoulder/arm-swing width plus margin; measure it. The Mid-360 on the G1 is **mounted upside down** ([deepglint](https://github.com/deepglint/FAST_LIO_LOCALIZATION_HUMANOID)) and sees the robot's own body, so crop a box around `base_link` before `pointcloud_to_laserscan`. Set the scan height band to cover table tops; the D435i or nvblox covers what the band misses.
- **Stairs:** the built-in controller handles standard residential stairs per one 2026 review, but a forum report says "climbing mode" stumbles ([review](https://roboticscenter.ai/en/blog/unitree-g1-review), [forum](https://forum.mybotshop.de/t/unitree-g1-edu-climbing-mode/1602)). Stair traversal reliability needs geometry-aware controllers ([arXiv 2605.09944](https://arxiv.org/html/2605.09944)). **Mark stairs and drop-offs as Nav2 keep-out zones**; single-floor only.
- **ROS lifecycle:** Humble EOL is May 2027; Jazzy runs to May 2029 ([endoflife.date](https://endoflife.date/ros-2)). Hydra, SysNav and Nav2's Following Server are Jazzy-first. Plan a Jazzy container move after the demo.

## 6. How the LLM planner should talk to navigation

Principles:

- **Long-running, asynchronous, cancellable.** Tools return a `task_id` at once. The agent polls or receives events. `stop()` / `cancel(task_id)` always works and maps to Nav2 action cancel. MCP bridges for Nav2 already expose navigate, waypoints, spin, cancel and clear-costmaps with velocity clamping and dry-run ([Amazing ROS 2 MCP](https://discourse.openrobotics.org/t/amazing-ros-2-mcp-native-ros-2-mcp-server-for-ai-assisted-robotics-agents/55270), [rosbridge-mcp cancel](https://glama.ai/mcp/servers/hieutachi/rosbridge-mcp/tools/cancel_action_goal)). DimOS uses the same MCP-skill pattern for a G1 ([GitHub](https://github.com/dimensionalOS/dimos)).
- **Symbolic targets, not coordinates.** The LLM picks `object_id` or `landmark`; the tool layer resolves them to a reachable pose (offset ~0.8 m, facing the object, snapped to free space). Raw `pose` stays available for debugging.
- **Feedback from Nav2:** `NavigateToPose` feedback = current pose, navigation time, **estimated time remaining, number of recoveries, distance remaining** ([Humble msg](https://docs.ros.org/en/humble/p/nav2_msgs/action/NavigateToPose.html), [API](https://api.nav2.org/actions/jazzy/navigatetopose.html)). Forward it as `{state, distance_remaining_m, eta_s, recoveries}`. Fail fast after K recoveries so the LLM can re-plan.
- **Structured failure reasons** (`goal_unreachable`, `localization_lost`, `blocked_by_person`, `target_not_seen`, `cancelled`) instead of free text. The LLM sees snapshots only, so it cannot handle moving obstacles itself; that stays in Nav2 ([NeuroCube design note](https://chanelfcheng.github.io/NeuroCube/new-navigation-system.html)).

Proposed tool surface:

| Tool                                                                   | Behaviour                                                                                                                                                       | Done when                                                      |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `navigate_to(target: {object_id \| landmark \| pose}, standoff_m=0.8)` | Resolve → NavigateToPose                                                                                                                                        | Nav2 SUCCEEDED, or failure reason                              |
| `find(query: str, max_time_s=180)`                                     | 1) object DB hit (fresh, confident) → navigate + verify. 2) Else `look_around()`. 3) Else LLM/VLM-ranked frontiers/rooms → explore → stop on verified detection | Target verified in view within 1 m, or timeout with best guess |
| `explore(region?: landmark, max_time_s)`                               | m-explore-ros2 (resume/pause), bounded by a region polygon                                                                                                      | No frontiers left / timeout                                    |
| `look_around()`                                                        | 360° in-place rotation in steps while the detector fills the object DB                                                                                          | Rotation complete; returns new objects                         |
| `follow_person(track_id?)`                                             | Lock the BoT-SORT track (nearest/speaker) → FollowPoint/FollowObject                                                                                            | `stop()`, target lost > timeout (→ `search_by_rotating`)       |
| `stop()` / `cancel(task_id)`                                           | Cancel all Nav2 actions, zero velocity                                                                                                                          | Immediate                                                      |
| `get_task(task_id)`                                                    | Status + feedback                                                                                                                                               | —                                                              |

### Compute placement

- **Orin NX:** Livox driver, FAST-LIO2, localization, Nav2 (MPPI is the heaviest; watch CPU), YOLO11n/YOLOE-S on TensorRT, BoT-SORT, object-DB writer, tool server.
- **Off-board (laptop/workstation GPU or cloud):** the LLM agent and any VLM (frontier ranking, verification crops). Every 2026 G1 object-nav system found does this: SysNav RTX 4090, OpenBelief-Nav RTX 5090, DRIVE-Nav off-board computation ([SysNav](https://gitee.com/EricGao2020/SysNav), [OpenBelief-Nav](https://arxiv.org/pdf/2608.13923)).
- **JetPack 6** only when you want Isaac ROS 3.x nvblox or GLIM onboard ([GLIM docs](https://koide3.github.io/glim/docker.html)); not needed for steps 0–7.

### Evaluation protocol

- **Success definition (Habitat ObjectNav):** the robot declares done within **1.0 m** of an instance of the target, with the object visible from there ([ObjectNav Revisited](https://ar5iv.labs.arxiv.org/html/2006.13171), [Stubborn](https://arxiv.org/pdf/2203.07359)).
- **Metrics:** SR; **SPL** = mean(Sᵢ · ℓᵢ / max(pᵢ, ℓᵢ)), where ℓᵢ is the shortest path from the map; time to success; distance-to-success on failures; human interventions/e-stops; LLM calls per task.
- **Task suites, ≥ 20 trials each, randomized start poses, 5–8 object classes incl. small ones (cup/glass, remote, bottle):**
  1. _Landmark nav_ ("go to the kitchen").
  2. _Memory ObjectNav_: object seen in a previous session.
  3. _Exploration ObjectNav_: object never seen; new placement.
  4. _Moved-object_: the DB is stale; tests forgetting and re-search.
  5. _Follow-me_: 3-minute walks with turns, a doorway and one occlusion; metrics = % time within 0.8–2.0 m, track-ID switches, losses.
  6. _Explore room_: % of free area covered vs ground truth after T minutes.
- **Baselines for the thesis:** (a) random/nearest-frontier exploration vs (b) LLM-ranked frontiers vs (c) memory-first. Optional (d) NaVILA. Report SR with Wilson 95% intervals; with 20 trials, ±~20 pp is normal, so present differences honestly.
- **Reference numbers:** SysNav reports near-100% real-world SR on 112 episodes _(secondary)_; OK-Robot 58.5% in messy homes ([arXiv 2401.12202](https://arxiv.org/html/2401.12202v2)); OpenFrontier 77% HM3D sim _(secondary)_.

## 8. Risks and open questions

- **2D scan on a swaying humanoid:** the scan plane tilts with gait, which can hurt slam_toolbox relocalization. That is why the 3D-localizer upgrade path exists. Validate early with a rosbag.
- **Glass and transparent objects** are weak for both the LiDAR and the D435i. A "glass" may have no valid depth, so fall back to box-bearing + LiDAR, or the table-surface height.
- **YOLO11n small-object recall at 2–4 m** is low. Use `look_around()` close-ups and an off-board VLM verification crop before declaring success.
- **Unofficial Unitree docs:** speed-mode values and SLAM-service details came from mirrors; confirm on support.unitree.com.
- **Not verified here:** the Nav2 Following Server is not in Humble (its Humble API page is boilerplate, [docs.ros.org](https://docs.ros.org/en/ros2_packages/humble/api/opennav_following/generated/index.html)), so use FollowPoint on Humble. Orin NX timings for MPPI + YOLO + FAST-LIO together were not found; measure them.
